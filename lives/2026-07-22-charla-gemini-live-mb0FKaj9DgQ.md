## What Gemini Live API offers (as presented)

- **What it is**: a real-time, bidirectional audio branch of Gemini. Speaker says it "officially launched in December" of the prior year but got little attention until OpenAI shipped its own live voice mode "last week" (`"a pesar de que ingresó primero... opena ya y sacó su chai titi en vivo"` (?) — reads as "even though it [Gemini Live] came first, OpenAI just shipped its live ChatGPT [voice mode]"), which is why he says interest spiked now.
- **Core value framed as two things real-time APIs give you**:
  - *"Experiencias nativas"* (native experience): not just conversing — reasoning happens directly in voice, with tone/idiom/emotion, so the user feels like they have someone next to them.
  - *"UX sin fricción"* (frictionless UX): audio in → audio out with no intermediate text round-trip. He explicitly contrasts this with the traditional pipeline: detect end-of-speech → transcribe audio to text → send text to LLM → LLM returns text → convert text to audio → send back. The Live model skips all of that. Analogy used: 2010's "pages must load in 2 seconds" bar — now users expect AI interaction to be just as instant.
- **Model used in the demo**: the "Flash" tier of the Live API, described as `"es el 3.1, es flash"` (?) — likely a mis-hearing of a version number (possibly "2.5"); later referred to as `"Gemini Flashlight Review"` (?), almost certainly "Gemini Flash **Live** **Preview**" — i.e. a **preview**, not GA, model. Docs page showed a training-data cutoff of "marzo de 2016" (?), i.e. March 2026.
- **Capabilities shown on the official model/capabilities page**: can think/reason, can respond, accepts tool inputs, can detect whether the user is talking, can detect if it's been interrupted, can generate audio, **cannot execute code** (audio-only model), and can call functions/tools (`"puede llamar la... opción"` (?), read as function/tool calling — listed but not demonstrated live).
- **Model comparison shown live in the model garden**: Gemini Pro = text in/out only (would need a second TTS model bolted on); a dedicated text-to-speech model = text in, audio out only; the Live model = audio in, audio out, real-time, function calling, cannot execute code. This is why he picks the Live model for anything that must "converse."
- **Architecture, two patterns named**: **client-to-server** and **server-to-server**. Only client-to-server was taught/demoed today (simplest); server-to-server was flagged as the production path, left as "read the docs / book time with me."
- **Pricing/limits mentioned**:
  - Live API has a free tier.
  - Registering for the **Google for Developers** program grants **$200** free credit for MVPs (separate program from Google AI Pro credit — a Q&A answer confirmed Google AI Pro credit does *not* apply here, that's for Antigravity/Gemini-in-email, not this GCP/dev-side product).
  - On cost vs. a DIY open-source STT+TTS pipeline: the integrated audio-in/audio-out Live model is described as price-competitive (`"este modelo tiene precios tan competitivos como..."`, comparison target garbled (?)), trading per-call cost for fewer moving parts, vs. a cheaper-per-piece but more-to-maintain open-source stack ("más lugares que mantener").
- **Code/architecture pattern shown**: a single HTML file with an ES module `<script type="module">`, importing a JS SDK with no install step (loaded directly, no npm mentioned). Config object needs: `apiKey`, `model`, `instructions` (system prompt), `modality` (`Text`/`Audio`/`Video` — exact enum unclear, transcribed as `"Trescos"` (?), possibly "one of three: audio, text, or video"), voice selection (172 voices available — robotic/andro­gynous/masculine/feminine; random voice picked if unspecified), interruption sensitivity, and an "empathy" toggle (model mirrors the user's emotional tone).

## Directly reusable for our voice inventory capture

- **Function/tool calling** is listed explicitly as a model capability (`"puede llamar la... opción"` (?), `"Tiene el Live Live"`) — this is the mechanism that would map "counter says '9 cajas de harina'" → a structured/validated record. **Caveat: not demonstrated in code during the talk**, only named on the capabilities page — we'd need to build and validate this ourselves against current docs.
- **System-prompt design rules for voice**, quoted directly because wording matters for a spoken confirm-back UX:
  - `"Regla crítica. Mantén tus respuestas cortas."` (critical rule: keep responses short) — because long spoken responses test poorly with users.
  - `"No uses listas con viñetas. Ni texto que suene raro al ser leído en voz alta."` (don't use bulleted lists, or text that sounds weird read aloud) — because dashes/bold/markdown literally get spoken as words ("uno punto, papá, dos puntos, arroz..."). Directly relevant to how we'd phrase count confirmations/anomaly flags back to the counter.
- **Prompt-engineering workflow he recommends**: describe your assistant's full intended behavior to Gemini Pro and ask it to generate an optimized system prompt for the Live model, since "Gemini knows its own models" and will produce a tighter, model-tuned prompt. Also: long/detailed instructions (200+ lines) are fine, and structuring them as JSON or Markdown helps the model parse them — relevant for encoding our ~1,400-item catalog rules, anomaly-flag logic, and fuzzy-matching guidance into the system prompt.
- **Interruption handling is configurable**, including sensitivity — his framing: `"¿qué tan delicados vamos a hacer con el tema de las interrupciones?"` (how sensitive do we make interruption detection — is a cough an interruption or not?). Directly relevant to a noisy warehouse floor.
- **Empathy/affect setting** — model can mirror user tone (matches sad/serious tone if the user is short/curt). Minor relevance: could make anomaly-flag conversations feel less robotic, but not core to our use case.
- **Language**: entire talk and live demo were conducted in Spanish, with the model answering fluently in Spanish (Latam-neutral accent from the speaker, Peru-based). **No explicit claim or test of Colombian-accent handling specifically** — general Spanish support was demonstrated, not dialect-specific accuracy.
- **Latency claim**: the whole pitch of the API is bypassing the STT→LLM→TTS chain for lower perceived latency — relevant to a "say it once, get fast confirmation" counting loop.
- **Notably, the live Q&A test case the speaker himself ran was a hotel/hospitality assistant**: he asked the demo agent `"cuéntame cómo podríamos usarte para hacer un ayudante para buscar hoteles"` (tell me how we could use you to build a hotel-search helper), and the model answered by discussing learning user preferences (location, price) and recommending matches from a set of options. This is hotel **search/recommendation**, not inventory counting — thematically adjacent to our Reto 4 vertical but not a blueprint for our workflow.

## Caveats & tensions

- **Offline requirement vs. Live API architecture — this is the central tension and the talk does not address it at all.** Both architecture patterns presented (client-to-server, server-to-server) are live, streaming connections to Google's backend; there is no on-device/offline mode, no Gemini Nano mention, no local-inference fallback, and no discussion of network-loss handling, reconnection, buffering-through-a-dropout, or queue-and-sync. The only network-related remark in the whole talk is about *speed*, not *availability*: `"todo depende de la velocidad de la red"` (playback pacing depends on network speed — chunks may arrive faster or slower and the client has to buffer/watermark them so words don't garble). **Nothing said about offline mode or on-device alternatives.**
- **Preview/non-GA status**: the model name itself contains "preview" (`"Live"` + `"preview"`), and the speaker frames this as inherently unstable/evolving — worth weighing for anything beyond a hackathon demo.
- **Docs freshness / AI-codegen risk**: because the API launched recently, general-purpose coding assistants may not have it indexed and can produce non-working code: `"si ustedes entran al mismo yemina y les ponen en quiero que me hagas esto, yemina se va a confundir"` (if you ask Gemini itself to build with this, Gemini will get confused) — same warned for other codegen tools/IDEs (mentions `"clave"` (?) probably Claude, and `"antigravity"`, Google's AI IDE). His recommendation: manually paste the official docs into whatever coding tool you use rather than trusting default knowledge.
- **Sample-rate is rigid, not just a config nicety**: input audio to the model **must** be 16kHz (`"Yamini solamente va a entender si nosotros le enviamos 16 kilogércitos"` (?) — Gemini will only understand audio sent at 16kHz/16000 sample rate; anything else, e.g. 16.1, gets nothing back) and the model's return audio channel is **always** 24kHz (`"si ponen 24-1, no les va a funcionar"` — mismatch breaks it). This is an unforgiving hardware/software integration detail for a tablet mic pipeline.
- **Live coding demo itself hit real errors** (undefined `mic` variable, had to restart twice) — not a substantive technical caveat about the API, but a reminder that this integration is fiddly to get right even for the author.
- **Cost note**: the $200 "Google for Developers" credit mentioned is a **separate program** from Google AI Pro subscriber credit and, presumably, separate from our own $300 hackathon sponsor credit — worth confirming these don't silently overlap/conflict when billing against the same GCP project.

## Q&A relevant bits

- **Dani**: isn't it better to pick a model sized to the robustness of the task, rather than always reaching for the flagship? Brian's answer: the task itself (real-time voice agent) constrains the choice — only models in the garden that accept audio-in/audio-out in real time are eligible at all; it's not a "pick the smallest capable model" question so much as "pick from the small subset that technically supports live audio."
- **Felipe**: how significant is the precision/quality gap between the Live model and Pro? Brian: depends on the goal — e.g. a simple "order a pizza" assistant doesn't need heavy reasoning, it needs good instructions. Precision/quality at this tier depends overwhelmingly on prompt engineering, not raw model power; using Pro would sacrifice real-time responsiveness for reasoning you likely don't need.
- **Yera Meraki**: does the model read the full instructions text before responding? Brian: yes — longer, more detailed instructions are fine and encouraged (no downside to 200+ lines), and structuring them as JSON or Markdown helps the model parse them better. He also referenced that leaked system prompts from major products/companies on GitHub are often huge, as reassurance that a long prompt is normal.
- **Dani Rosa**: could you swap in an open-source STT+TTS pipeline instead of the native-audio model? Brian: yes, that's a valid alternative — cheaper/freer per-component potentially, but more separate systems to maintain and more failure points ("más lugares que mantener") versus one integrated audio-in/audio-out model at a competitive price.
- **Gerard**: does having Google AI Pro give extra credit for this? Brian: no — Google AI Pro credit is for a different surface (Antigravity, Gemini in email/Workspace, etc.); the Live API / GCP dev-side credit comes only through the Google for Developers program ($200 mentioned above).

## Verdict: how we'd use this in the reto (3–5 bullets, honest about the offline conflict)

- **The offline requirement is not solvable with Gemini Live API as presented.** Both architectures shown (client-to-server, server-to-server) are live network calls to Google; the talk offers zero on-device/offline story. For bodegas without network we need a separate local path (on-device/offline STT + local fuzzy match against the cached ~1,400-item catalog, queue results, sync/reconcile against Gemini-assisted validation once connectivity returns) — Live API can only cover the "has network" bodegas directly.
- **Function/tool calling is our best lever for "utterance → structured record"**, but it was only named as a capability, never coded live — we should prototype it ourselves against current docs (and heed the speaker's warning that codegen tools may hallucinate against this preview API; paste the real docs into whatever assistant we use to build it).
- **The system-prompt rules for voice (short answers, no bullet/markdown formatting, tune interruption sensitivity for background noise) transfer directly** to how we'd phrase spoken confirmations and anomaly flags back to a counter on a noisy warehouse floor.
- **16kHz-in/24kHz-out is a hard, unforgiving constraint** to design the tablet's mic capture pipeline around from day one, not something to discover mid-build.
- **Preview-model status + no offline mode together argue for using Gemini Live API as an "online-mode enhancement" (fast confirm-back, fuzzy-match assist, anomaly narration) rather than the sole capture mechanism** — the core blind-count-and-validate logic should not have a hard runtime dependency on a live connection to Google.
